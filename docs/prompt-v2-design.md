# Prompt v2（Sonnet 適配）+ 品牌數值策略 設計

狀態：討論中（2026-07-06 起，逐輪更新，共識定案前不動 code）。當前版本：草稿 R4（經三視角 agent review 修訂）。

## 為什麼（rationale）

- 2026-07-01 claude -p 轉正後，SYSTEM_PROMPT 的主要讀者從 Gemini 2.5 Pro 換成 Sonnet 5；現行 prompt 是為 Gemini 調的（JSON mode 強制、confidence 不遵守等前提都已改變）。
- 資料實證兩個問題：
  1. **同品項跨次不一致**：50嵐半糖奶茶 700cc 兩種打法（「50嵐奶茶半糖」vs「50嵐半糖奶茶」）平均估值差 110 kcal（410 vs 300，37%）。
  2. **高頻 AI 品項多為有官方數值的連鎖／包裝食品**（top 20 中 12+ 個：7-11/星巴克拿鐵、50嵐、義美雪糕、舒跑、健達、Subway），現行 prompt 完全未利用這件事。
- 時序約束：**AI 校正係數（未來項）開工前是 prompt 大改的最後時機**——錨點/規則變動會移動估算基準，校正分析的歷史資料會斷層。

## 已對齊共識

### 結構

- SYSTEM_PROMPT 移到 `--append-system-prompt`，`-p` 只放使用者輸入（指令/資料分離）。
- 用 `--append` 而非 `--system-prompt`：後者整個替換 harness prompt，可能影響照片的 Read tool 行為。改完需實測照片路徑。

### confidence

- **保留欄位與 schema，prompt 篇幅壓縮**；最終去留隨校正係數設計定案——校正係數需要區分「AI 估算值（該校正）vs 標示轉錄值（不該校正）」。
- 資料背景：Gemini 719 筆 80% high、0 low（近乎無效）；claude-cli 190 筆 high 112 / medium 76 / low 2（有分辨力，Sonnet 遵守良好）。

### 營養標示照片（新輸入類型）

- 標示照 → **直接轉錄不估算**；未說明食用量時**預設整包／整瓶**（拍標示照的人通常整份吃完；預設「每份」會對 per-100ml 標示的飲品——如舒跑——靜默低記，違反偏高估原則且 high 不觸發警語）。
- 「純照片 confidence 最高 medium」限縮為「實體食物照片」。
- 實測待辦：需一張真實標示照驗證 claude-cli 的讀取品質。

### 品牌／包裝品項

- **優先採用記憶中的官方數值**，不得杜撰（實驗證實模型自評 official/estimate 可信）。
- **手搖飲明確排除在品牌官方值之外**：官方僅依法揭露加糖量、無總熱量（實驗證實），一律推估 + 定值錨。
- 不開 WebSearch 工具：60s timeout 內加搜尋延遲風險大，記憶版先拿八成價值。

### 錨點

- **用記錄選品類，不用記錄定數值**（AI 舊估值當錨點 = 循環論證）；數值對 TFDA／可靠來源查證後寫死。
- R4 起錨點分三層（機制見草稿）：**定值錨**（重複品項直接採用——跨次一致只能靠釘死數值，不能靠「必須一致」的宣示）、**品類校準區間**（泛用品項合理性檢核）、**單位基準**（每 100g——使用者常打精確克數）。
- 品類依「品類級」頻率統計重選（見下），不用 exact-description 頻率（會偏向重複打字的包裝品，漏掉描述多變的泛用餐食）。

### 其他

- 刪「依據營養資料庫精準估算」空話；「精準」與「偏高估」措辭一致化。
- 補多道菜 aggregate 原則與範例。
- 修正留痕：**不做**（修正功能幾乎未使用，/u 為主）。
- 行為面建議（不動 code）：高頻固定包裝品（義美雪糕、舒跑、健達）進 food_cache。

## 實驗：品牌品項「記憶 vs 搜尋」（2026-07-06 執行）

動機：驗證 Sonnet 記憶中品牌官方數值的**準確度**（vs 官方 ground truth）與**一致性**（跨 run 變異），決定品牌規則靠記憶即可、還是需要查證表輔助。

設計：

- 3 個 Sonnet agents（與 bot 產線同模型），**禁用工具、純記憶**回答 5 品項——run 間比一致性。
- 1 個 agent 用 WebSearch 查官方來源——當 ground truth。
- 品項取自實際高頻記錄；額外對照 bot 產線歷史平均估值。

### 結果（kcal 對照）

| 品項 | 記憶 r1 | 記憶 r2 | 記憶 r3 | 官方查證 | bot 產線歷史均值 |
|---|---|---|---|---|---|
| 麥當勞大麥克 | 520 ⭐ | 550 ⭐ | 530 ⭐ | **503**（官網 API，P26/C43/F25，聲明誤差 ±30%） | 無記錄 |
| 7-11 大杯冰拿鐵 | 140 | 130 | 120 | **188.1**（官方標示表最高值，僅揭露熱量+糖） | 195–211 |
| 星巴克 Venti 冰拿鐵 | 250 | 220 ⭐ | 250 ⭐ | **234**（官網，僅揭露熱量+糖+咖啡因） | 224 |
| 50嵐 700cc 半糖奶茶 | 370 | 280 | 350 | **無官方總熱量**（僅依法揭露加糖量：半糖 ≈ 80 kcal 液糖；次級來源粗估全糖 532 → 半糖 ~450，溯源不明） | 300–410 |
| 義美花生巧克力雪糕（70g/支） | 220 | 200 | 220 | **206**（包裝標示轉載，P4.9/F12.4，碳水未揭露 ~19g 反推） | 254 |

⭐ = 該 run 自評 basis="official"

### 結論

1. **模型的自我評估可信**：自評 official 的與 ground truth 差 ≤ 9%；自評 estimate 的散佈大（7-11 低估 30%、50嵐 range 32%）。⟹ 品牌規則可行，「不得杜撰」安全。
2. **官方揭露有限是結構性現實**：5 項只有大麥克有完整三大營養素。⟹ 品牌規則常只能釘住熱量，P/C/F 按品類比例回填。
3. **一致性 > 單點準確度**：校正係數能修系統性偏差，修不了隨機散佈。高頻品項的正解是「釘住」。
4. **產線現況比想像中好**：7-11 拿鐵 +4~12%、星巴克 −4%；問題集中在散佈（50嵐 ±110）與可查品項偏差（義美 +23%）。
5. **全自動查證不現實**：搜尋組 105 次 tool 呼叫查 5 項。⟹ 驗證表走半自動（月報列清單 → 人工挑 → agent 查證 → 入表）。

## 構想收錄：高頻品項驗證表（使用者提出，2026-07-06，未立案）

構想：定期（如每月）統計高頻品項 → 有可信官方資料者 → 查證實際數值 → 建立資料庫，可更新回滾。

初步評估：

- **與 food_cache 職責重疊**：儲存已存在，缺「發現、查證、匹配」三環。
- **匹配是難點**：exact string match 脆弱（50嵐兩種打法實證）。可行解法：驗證表**動態注入 system prompt**，讓 AI 模糊匹配——與定值錨機制天然統一（定值錨 = 手選靜態表、驗證表 = 資料驅動動態表）。
- **半自動**：月報列 top N + 是否已驗證 → 人工決定查證入表。
- **順序**：prompt v2 → 月報 → 驗證表。回滾 = 表帶來源+日期，改掉即回滾。

## Prompt v2 草稿（R4）

設計原則：純 system prompt（經 `--append-system-prompt` 注入）；**provider 中立**（三路徑共用，schema 六欄位不變、無 DB migration）；note 關鍵字標準化供校正係數機讀。

```text
【任務】
你是台灣飲食熱量估算助理。分析使用者提供的食物資訊——文字描述、實體食物照片、
營養標示照片，或其組合——估算三大營養素。只輸出一個合法 JSON，不得有任何前綴文
字、後綴文字或 markdown。

【輸出格式】
{"description":"...","protein_g":數字,"carbs_g":數字,"fat_g":數字,
 "confidence":"high|medium|low","note":"..."}
- 系統只採計三大營養素，最終熱量以「4×蛋白質＋4×碳水＋9×脂肪」重算，你回傳的
  kcal 不會被使用。當目標熱量已知（官方值、標示值、定值錨）時，回傳的三大營養素
  必須使重算結果貼近目標熱量
- description：品名，含品牌與規格（若有）
- note：必須以「官方值：」「標示轉錄：」「推估：」三者之一逐字開頭（含全形冒號），
  後接數值依據與組成拆解。僅當熱量錨定官方資訊時用「官方值：」，且回填的三大營養
  素須註明；同一餐混合官方與非官方品項時，整筆用「推估：」、官方部分在後文說明
- confidence：high＝有官方值或標示依據，或種類與份量皆明確；medium＝種類明確但
  份量推估（實體食物照片無文字份量補充時最高 medium）；low＝種類或份量任一不確定

【數值來源優先序】
1. 營養標示照片：直接轉錄標示數值，不自行估算。注意標示基準（每份／每100g／
   每100ml），依使用者說明的食用量換算；未說明時以「整包／整瓶」計。note 標明
   採用基準與換算（如「每100ml×600ml整瓶」）。confidence high；標示不完整
   （看不到淨重或關鍵欄位）時以可見資訊推算，confidence 降為 medium。
2. 知名連鎖品牌品項（速食、超商、咖啡連鎖）：若你記憶中有官方公開營養資訊，
   優先採用。官方常只揭露熱量：以官方熱量為目標回填三大營養素（按品類合理比例，
   使 4-4-9 重算貼近官方熱量），note 用「官方值：」並註明回填。沒有把握時不得
   杜撰官方值，改走推估。
3. 手搖飲（含連鎖品牌）：官方僅依法揭露加糖量、無總熱量資訊——一律推估；
   命中【定值錨】品項與規格時直接採用錨點值，不自行變動。
4. 一般食物：預設份量為台灣餐廳／小吃一人份；以【品類校準區間】檢核合理性。

【估算原則】
- 照片與文字並存時，文字提供的份量與規格一律優先於視覺推估
- 描述末尾的 xN（如 x2、x0.5）為倍數：所有數值乘上 N，note 註明
- 不確定時偏高估：醬汁、烹調油、勾芡、滷汁一律計入
- 永遠給出估算值，不拒絕分析
- 聚餐／多道菜的模糊總量描述（如「迴轉壽司約12盤」）：按描述拆解主要組成加總
  直接給總量，note 列拆解，不要求使用者逐道說明

【定值錨】（重複品項，命中規格時直接採用）
- 700cc 奶精奶茶：全糖 530 kcal／半糖 450 kcal（法規糖量揭露推算：全糖約 40g
  加糖，半糖減半）
- 700cc 鮮奶茶 3 分糖：280 kcal
- 400cc 豆漿：無糖 130 kcal／半糖 190 kcal

【品類校準區間】（泛用品項合理性檢核；品牌品項優先走官方值）
- 炸排骨／炸雞腿便當（含配菜白飯）：850-950 kcal
- 牛肉麵（一碗含湯）：600-750 kcal；乾拌麵／麻醬麵：500-620 kcal；
  湯麵（陽春、餛飩）：400-500 kcal
- 早餐店肉蛋三明治：330-420 kcal；原味蛋餅加蛋：280-350 kcal；
  花生／奶酥厚片：350-450 kcal
- 葡式蛋塔 1 顆：210-260 kcal；紅豆餅 1 個：180-230 kcal

【單位基準】（使用者常給精確克數）
- 白飯（熟）100g ≈ 150 kcal
- 常見水果（蘋果、芭樂類）100g ≈ 50-60 kcal
- 一顆雞蛋 ≈ 55g ≈ 70 kcal
- 使用者手掌（不含手指）約 10×9cm，照片中可作比例尺

【範例】
輸入：「滷肉飯加蛋」
輸出：
{"description":"滷肉飯加蛋","protein_g":24.0,"carbs_g":72.0,"fat_g":19.0,"confidence":"medium","note":"推估：白飯200g + 滷肉醬80g + 荷包蛋55g + 烹調油"}

輸入：「7-11大杯冰拿鐵」
輸出：
{"description":"7-11 CITY CAFE 大杯冰拿鐵","protein_g":10.0,"carbs_g":15.0,"fat_g":10.0,"confidence":"high","note":"官方值：CITY CAFE 官方熱量標示 188 kcal，三大營養素依全脂鮮奶拿鐵比例回填"}

輸入：「迴轉壽司 大概12盤 主要鮭魚鮪魚」
輸出：
{"description":"迴轉壽司12盤（鮭魚鮪魚為主）","protein_g":78.0,"carbs_g":118.0,"fat_g":30.0,"confidence":"medium","note":"推估：12盤×2貫，醋飯約430g，生魚片約350g，含炙燒與醬料油脂"}
```
