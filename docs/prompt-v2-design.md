# Prompt v2（Sonnet 適配）+ 品牌數值策略 設計

狀態：討論中（2026-07-06 起，逐輪更新，共識定案前不動 code）

## 為什麼（rationale）

- 2026-07-01 claude -p 轉正後，SYSTEM_PROMPT 的主要讀者從 Gemini 2.5 Pro 換成 Sonnet 5；現行 prompt 是為 Gemini 調的（JSON mode 強制、confidence 不遵守等前提都已改變）。
- 資料實證兩個問題：
  1. **同品項跨次不一致**：50嵐半糖奶茶 700cc 兩種打法（「50嵐奶茶半糖」vs「50嵐半糖奶茶」）平均估值差 110 kcal（410 vs 300，37%）。
  2. **高頻 AI 品項多為有官方數值的連鎖／包裝食品**（top 20 中 12+ 個：7-11/星巴克拿鐵、50嵐、義美雪糕、舒跑、健達、Subway），現行 prompt 完全未利用這件事。
- 時序約束：**AI 校正係數（未來項）開工前是 prompt 大改的最後時機**——錨點/規則變動會移動估算基準，校正分析的歷史資料會斷層。

## 已對齊共識

### 結構

- SYSTEM_PROMPT 移到 `--append-system-prompt`，`-p` 只放使用者輸入（指令/資料分離）。
- 用 `--append` 而非 `--system-prompt`：後者整個替換 harness prompt，可能影響照片的 Read tool 行為。改完需實測照片路徑。

### confidence

- **保留欄位與 schema，prompt 篇幅壓縮**（兩段合一段）；最終去留隨校正係數設計定案——校正係數需要區分「AI 估算值（該校正）vs 標示轉錄值（不該校正）」，confidence 是現成載體。
- 資料背景：Gemini 719 筆 80% high、0 low（近乎無效）；claude-cli 190 筆 high 112 / medium 76 / low 2（有分辨力，Sonnet 遵守良好）。唯一行為分支 low → 警語（`meal.py:122`），190 筆僅觸發 2 次。

### 營養標示照片（新輸入類型）

- 標示照 → **直接轉錄不估算**，處理「每份 / 每 100g / 整包」換算，note 標明採用基準，confidence high。
- 現行「純照片 confidence 最高 medium」限縮為「實體食物照片」——標示照是精確資料，cap 在 medium 是反著教。
- 實測待辦：需一張真實標示照驗證 claude-cli 的讀取品質（Gemini 時代已驗證可讀）。

### 品牌／包裝品項

- 方向確立：**優先採用官方數值**（模型記憶中有麥當勞、超商、連鎖手搖的公開營養資訊；Gemini「會查真實數字」實為記憶背誦，該管線無搜尋能力，Claude 機制相同、只差沒被指示優先使用）。
- 實作深度（純 prompt 規則 vs 驗證表輔助）由實驗結果決定（見下）。
- 不開 WebSearch 工具：60s timeout 內加搜尋延遲風險大，記憶版先拿八成價值。

### 錨點

- **用記錄選品類，不用記錄定數值**——meal 記錄的數值是 AI 自己估的，拿舊估值當錨點是循環論證。記錄的正確用途 = 頻率分析（哪些品類值得錨定）。
- 品類調整方向：便當、早餐店、甜點類（泛用小吃）；連鎖／包裝品項不靠錨點、靠品牌規則。
- 數值：對 TFDA 或可靠來源查證後寫死，不再用拍腦袋數字。

### 其他

- 刪「依據營養資料庫精準估算」空話（資料庫不存在）；「精準」與「偏高估」措辭一致化。
- 補一條多道菜 aggregate 範例（README 主打場景，現靠模型硬扛）。
- 修正留痕：**不做**——修正功能幾乎未使用（使用者以 /u 刪除重記為主），投資無回報。
- 行為面建議（不動 code）：高頻固定包裝品（義美雪糕、舒跑、健達）進 food_cache，官方數值一次填對，之後免 AI。

## 實驗：品牌品項「記憶 vs 搜尋」（2026-07-06 執行）

動機：驗證 Sonnet 記憶中品牌官方數值的**準確度**（vs 官方 ground truth）與**一致性**（跨 run 變異），決定品牌規則靠記憶即可、還是需要查證表輔助。

設計：

- 3 個 Sonnet agents（與 bot 產線同模型），**禁用工具、純記憶**回答 5 品項——run 間比一致性。
- 1 個 agent 用 WebSearch 查官方來源——當 ground truth。
- 品項取自實際高頻記錄：麥當勞大麥克、7-11 大杯冰拿鐵、星巴克 Venti 冰拿鐵、50嵐 700cc 半糖奶茶、義美花生巧克力雪糕。
- 額外對照組：bot 產線歷史平均估值（meals 表，現行 prompt 下的實際輸出）。

### 結果（kcal 對照）

| 品項 | 記憶 r1 | 記憶 r2 | 記憶 r3 | 官方查證 | bot 產線歷史均值 |
|---|---|---|---|---|---|
| 麥當勞大麥克 | 520 ⭐ | 550 ⭐ | 530 ⭐ | **503**（官網 API，P26/C43/F25，聲明誤差 ±30%） | 無記錄 |
| 7-11 大杯冰拿鐵 | 140 | 130 | 120 | **188.1**（官方標示表最高值，僅揭露熱量+糖） | 195–211 |
| 星巴克 Venti 冰拿鐵 | 250 | 220 ⭐ | 250 ⭐ | **234**（官網，僅揭露熱量+糖+咖啡因） | 224 |
| 50嵐 700cc 半糖奶茶 | 370 | 280 | 350 | **無官方總熱量**（僅依法揭露加糖量：半糖 ≈ 80 kcal 液糖；次級來源粗估全糖 532 → 半糖 ~450，溯源不明） | 300–410 |
| 義美花生巧克力雪糕（70g/支） | 220 | 200 | 220 | **206**（包裝標示轉載，P4.9/F12.4，碳水未揭露 ~19g 反推） | 254 |

⭐ = 該 run 自評 basis="official"（自認是記憶中的官方值而非推估）

### 結論

1. **模型的自我評估可信**：自評 official 的（大麥克 ×3、星巴克 ×2）與 ground truth 差 ≤ 9%；自評 estimate 的散佈大（7-11 低估 30%、50嵐 range 32%）。⟹ prompt 品牌規則可行，且「模型自認 official/estimate」是可靠訊號，可要求寫進 note；未來驗證表的查證對象排序也能用它（高頻 × 自評 estimate = 優先查證）。
2. **官方揭露有限是結構性現實**：5 項只有大麥克有完整三大營養素；7-11/星巴克只給熱量；50嵐只給加糖量；義美靠包裝標示。⟹ 品牌規則常只能釘住熱量，P/C/F 仍需模型按品類比例回填（prompt 指示：官方熱量為準、macros 合理分配、note 說明）。
3. **一致性 > 單點準確度**：校正係數能修系統性偏差，修不了隨機散佈。高頻品項的正解是「釘住」——速食/星巴克靠記憶官方值、包裝品靠標示照轉錄或 cache、手搖飲靠自定錨（官方資料不存在，挑一個值用到底）。
4. **產線現況比想像中好**：7-11 拿鐵 195–211 vs 官方 188（+4~12%）、星巴克 224 vs 234（−4%）；問題集中在散佈（50嵐 ±110）與可查品項的偏差（義美 +23%）。
5. **全自動查證不現實**：搜尋組花了 105 次 tool 呼叫才查完 5 項（含爬官方 PDF、營養 API）。⟹ 驗證表走半自動（月報列清單 → 人工挑 → agent 查證 → 入表）是對的粒度。

### 實驗結論對設計的落地（建議，待使用者確認）

- prompt 品牌規則措辭：「知名連鎖品牌品項，若記憶中有官方營養資訊，優先採用並於 note 標註『官方』；沒有把握就正常估算，**不得杜撰官方值**」（實驗顯示模型誠實，此規則安全）。
- 手搖飲另立一條：無官方營養資料的品類（手搖飲），同規格重複品項力求跨次一致；長期解為 cache/錨點。
- 高頻品項驗證表構想**獲實驗支持**，維持順序：prompt v2 → 月報 → 驗證表。

## 構想收錄：高頻品項驗證表（使用者提出，2026-07-06，未立案）

構想：定期（如每月）統計高頻品項 → 有可信官方資料者（拿鐵、麥當勞）→ 查證實際數值 → 建立資料庫，可更新回滾。

初步評估：

- **與 food_cache 職責重疊**：儲存機制已存在。真正缺的是三件事——(a) 發現（哪些品項高頻）、(b) 查證（官方數值哪裡來）、(c) 匹配（自由文字輸入 → 認出對應驗證條目）。
- **匹配是難點**：exact string match 脆弱（50嵐兩種打法即實證）。可行解法：驗證表**動態注入 system prompt**，讓 AI 自己做模糊匹配並採用官方值——這與錨點機制天然統一（錨點 = 手選靜態表、驗證表 = 資料驅動動態表）。
- **自動化程度建議半自動**：月報列出 top N 品項 + 是否已驗證 → 人工決定是否查證入表。單人維護導向，「來源可信度」的判斷不宜全自動。
- **依賴與順序**：prompt v2（靜態規則 + 錨點）先行 → 月報 → 驗證表。驗證表是月報的衍生功能。
- **回滾**：表帶來源 + 日期欄位，更新／刪除即回滾，不需專門機制。

## Prompt v2 草稿（R3，逐輪修正）

設計原則：寫成純 system prompt（經 `--append-system-prompt` 注入，`-p` 只放使用者輸入）；**維持 provider 中立**（Gemini / Claude API 路徑共用同一份，schema 六欄位不變、無 DB migration）；數值依據用 note 關鍵字標準化（「官方值」「標示轉錄」「推估」），供未來校正係數區分。

```text
【任務】
你是台灣飲食熱量估算助理。分析使用者提供的食物資訊——文字描述、實體食物照片、
營養標示照片，或其組合——估算三大營養素。只輸出一個合法 JSON，不得有任何前綴文
字、後綴文字或 markdown。

【輸出格式】
{"description":"...","protein_g":數字,"carbs_g":數字,"fat_g":數字,
 "confidence":"high|medium|low","note":"..."}
- description：品名，含品牌與規格（若有）
- note：一句話交代數值依據，開頭標明類型：「官方值」「標示轉錄」或「推估」，
  後接組成拆解或換算說明
- confidence：high = 有官方值或標示依據，或種類與份量皆明確；
  medium = 種類明確但份量推估（實體食物照片無文字份量補充時最高 medium）；
  low = 種類或份量任一不確定

【數值來源優先序】
1. 營養標示照片：直接轉錄標示數值，不自行估算。注意換算基準（每份／每 100g／
   整包），依使用者說明的食用量換算；未說明時以「每份」計。note 標「標示轉錄」
   與採用基準。confidence high。
2. 知名連鎖品牌品項（速食、超商、咖啡與手搖連鎖）：若你記憶中有官方公開營養
   資訊，優先採用，note 標「官方值」。官方常只揭露熱量：以官方熱量為準，三大
   營養素按品類合理比例回填並說明。沒有把握時不得杜撰官方值，改走推估。
3. 無官方資料的品類（如手搖飲）：依配方組成推估，並以下方錨點為基準——同一
   品項同一規格，不論描述詞序如何，每次估算數值必須一致。
4. 一般食物：預設份量為台灣餐廳／小吃一人份；使用者補充份量優先採用。

【估算原則】
- 不確定時偏高估：醬汁、烹調油、勾芡、滷汁一律計入
- 永遠給出估算值，不拒絕分析
- 聚餐／多道菜的模糊總量描述（如「迴轉壽司約12盤」）：按描述拆解主要組成
  加總直接給總量，note 列拆解，不要求使用者逐道說明

【常見錨點】（泛用品項校準用；品牌品項優先走官方值）
- 炸排骨／炸雞腿便當（含配菜白飯）：850-950 kcal
- 滷肉飯（一碗）：400-500 kcal
- 蛋炒飯（餐廳一盤）：680-800 kcal
- 早餐店肉蛋三明治：330-420 kcal
- 葡式蛋塔 1 顆：210-260 kcal；紅豆餅 1 個：180-230 kcal
- 燙青菜＋肉燥一匙：90-120 kcal
- 700cc 奶精奶茶：全糖 500-550 / 半糖 420-470 kcal（依法規加糖量揭露推算：
  全糖約 40g 加糖，半糖減半）；700cc 鮮奶茶 3 分糖：250-300 kcal

【視覺份量參考】
- 使用者手掌（不含手指）約 10×9cm，照片中可作比例尺
- 一顆雞蛋 ≈ 55g

【範例】
輸入：「滷肉飯加蛋」
輸出：
{"description":"滷肉飯加蛋","protein_g":24.0,"carbs_g":72.0,"fat_g":19.0,"confidence":"medium","note":"推估：白飯200g + 滷肉醬80g + 荷包蛋55g + 烹調油"}

輸入：「麥當勞大麥克」
輸出：
{"description":"麥當勞大麥克（單點）","protein_g":26.0,"carbs_g":43.0,"fat_g":25.0,"confidence":"high","note":"官方值：台灣麥當勞公開營養資訊，約503 kcal"}

輸入：「迴轉壽司 大概12盤 主要鮭魚鮪魚」
輸出：
{"description":"迴轉壽司12盤（鮭魚鮪魚為主）","protein_g":62.0,"carbs_g":105.0,"fat_g":28.0,"confidence":"medium","note":"推估：12盤×2貫，醋飯約430g，生魚片約350g，含炙燒與醬料油脂"}
```

### 對 v1 的變更對照

| 變更 | 對應共識 |
|---|---|
| 刪「依據營養資料庫精準估算」；任務段改寫 | 空話清理 |
| 新增【數值來源優先序】四層（標示轉錄 > 品牌官方值 > 錨點推估 > 一般推估） | 營養標示 + 品牌規則 + 手搖飲一致性 |
| 「純照片 cap medium」限縮為「實體食物照片」，併入 confidence 定義 | 標示照是精確資料 |
| confidence 兩段壓成輸出格式內三行 | confidence 壓縮 |
| note 開頭標準化關鍵字（官方值／標示轉錄／推估） | 校正係數的估算 vs 轉錄區分（暫不動 schema） |
| 錨點品類重選：+早餐店三明治、蛋塔、紅豆餅、奶精奶茶（含糖量計算基準）；品牌品項移出錨點職責 | 用記錄選品類、不用記錄定值 |
| 新增多道菜原則 + 範例；新增大麥克官方值範例（數值取自本實驗查證：503 kcal P26/C43/F25） | 多道菜補強 + 品牌規則示範 |
| 手掌比例尺、偏高估、永不拒絕：保留 | 無異議沿用 |

### 實作骨架（invocation 改動，隨 prompt v2 一起上）

cmd = [
    CLAUDE_CLI_PATH, "-p", "\n".join(user_parts),
